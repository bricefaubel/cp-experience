01 — Diagnosis

The business is generating valuable signals and giving away the value

Connected equipment produces exactly what a dealer's business runs on — early failure warning, evidence for service agreements, justification for replacement quotes. The portal converts almost none of it into scheduled work. Low daily engagement is not the problem; it is the symptom of a product with no daily job.

  • 01Notifications default to None. All three alert types, both primary and secondary email. The product cannot reach a dealer unless the dealer initiates contact.
  • 02Duplicates are not collapsed. One property produced three identical zone communication faults inside the same minute, each occupying its own row in a 96-item list.
  • 03Faults ship as codes. 184-IDU DISSIP. BOARD COMM FAULT — no meaning, no likely cause, no recommended action.
  • 04The predictive engine is manual. Malfunction Detection only runs when someone remembers to press "Run a Report."
  • 05Diagnosis takes four screens. Dashboard → Customers → Property Details → Control Details, then an accordion — ending at ~50 raw config fields in flat alphabetical order.
02 — The bet
Dealers will never habitually visit a portal. The portal must arrive in their morning already sorted.

Everything in this document follows from that sentence. If a design decision does not make the dealer's morning triage faster or more confident, it does not belong in v1.

Primary user

Service manager

Three to eight techs to route, imperfect information, under time pressure. "In five minutes, tell me which customers need a truck today and why."

Secondary

Service technician

Needs diagnosis-grade depth once assigned. "Before I knock on the door, tell me what's likely wrong and what to bring."

Secondary

Dealer principal

Checks weekly. "Is this thing earning its keep?"

Out of scope — v1

Distributors, revenue framing

Roll-up views and commercial triggers belong to Option B. Deliberately excluded to keep v1 shippable.

03 — Concept model

One new object: the Incident

An alert is one raw event from one piece of equipment at one moment. An incident is a situation at a property that may require human action — every related alert from the same system, grouped, ranked, and named in plain language.

Three levels, not four — four invites indecision. Priority is computed from severity × occurrence count × persistence × equipment criticality × season, and every priority carries a shape as well as a colour so it survives red-green colour blindness and a bad monitor in a back office.

05 — Screens

Five surfaces

5.1 — replaces Dashboard

Triage queue

Grouped by priority, not sorted by timestamp. Day header, three collapsible bands, row-level acknowledge / create work order / dismiss, bulk select. The five counter tiles are removed — inventory metrics are not work; they move to Performance.

5.2 — replaces the 4-click journey

Incident detail

What is happening · why it matters · what we'd check first · actions · property · equipment · timeline · live state. The ~50 config fields survive but collapse behind "advanced," grouped by function rather than alphabet.

5.3 — highest leverage

Notifications & delivery

Defaults flip from None to on. SMS as a first-class channel. Routing by role, not by email slot. Quiet hours and a volume preview — the answer to "will this spam me." The daily digest is arguably the real product; design it.

5.4

Malfunction detection

Screening runs on a schedule. Findings enter the queue as incidents in the same language as fault-driven ones. The dedicated view survives as a trend-and-accuracy screen — that is how Pro earns renewal.

5.5 — deliberately thin

Performance

Weekly cadence for the owner: incidents raised, acknowledged, converted; median time to acknowledgement; connection rate; prediction accuracy; the relocated counters.

Voice rule

Sentence case, always

No shouting caps in labels. Name things by what the dealer controls, not how the system is built.

Voice rule

Actions keep their name

The button that says Create work order produces a confirmation that says Work order created.

Voice rule

Empty is an invitation

Errors say what happened and what to do next. Empty screens don't apologise — they tell you the fleet is healthy.

07 — Integration

One load-bearing dependency

SystemDirectionRequirement
FSM backendwriteCreate work order pushes an incident into the dealer's FSM, pre-populated with customer, equipment, diagnosis and likely causes. This is the integration everything else rests on.
FSM backendreadWork order status returns to the incident so the queue knows what has been scheduled and closed.
Technician appwriteIncident detail, including first-check guidance, reaches the assigned tech.

Notification servicewriteEmail and SMS delivery with per-role routing.
Fallback requirement

If bidirectional FSM write is unavailable for a given dealer, Create work order degrades to an exportable, copyable, emailable job packet. Design both states — demonstrated in the prototype above.

08 — Design direction

Decisive, not decorative

Connected Portal lives inside the HVAC Partners shell and must not look like a different product. Work with the existing frame — near-black global nav, cool neutral page, Carrier blue reserved for actions. Spend the design's energy on the priority system.

Colour

Priority owns the palette

Saturated red-orange for act today, used nowhere else in the product. Warm amber for this week, different in hue and value. Low-chroma slate for watch. Blue never carries status; it only carries action.

Type

Mono separates meaning from provenance

A body face for the plain-language content — now the majority of on-screen text. A heavier weight of the same family for titles. Mono for codes, serials, models and timestamps, so a tech can scan a serial against a physical unit.

Density

Eight incidents above the fold

Today's product oscillates between too dense (Control Details) and too airy (Dashboard). Dense enough to see the day at once; calm enough that priority reads before you focus on it.

Signature

The day header

One sentence of plain English, set large, that changes every morning and tells a dealer whether today is a normal day. Everything around it stays quiet. This is the thing that makes the portal feel like it works for them rather than storing things about them.

Restraint

No dashboard chrome

No sparklines, no gauges, no counter tiles. This is a work queue. The current product's failure was ornamental reporting — do not repeat it in a nicer font.

Floor

Triage without a mouse

Full keyboard operation of the queue, visible focus, AA contrast on every priority indicator, screen-reader-legible priority, reduced motion respected.

10 — Sequencing

Order is not negotiable

Phase 1

Make it trustworthy

Incident grouping, priority model, plain-language content, queue screen. No notifications yet.

Phase 2

Make it arrive

Notification defaults, role routing, digest design, SMS. Only after Phase 1 proves grouping is right.

Phase 3

Make it convert

FSM work order write, technician app handoff, automatic malfunction screening.

Phase 4

Make it accountable

Performance view, prediction accuracy, dismissal-reason feedback loop.

The failure mode

Phase 2 must not ship before Phase 1 is validated. Turning on notifications against an ungrouped, unranked stream is a one-shot trust event — dealers mute the channel and never come back. This is also the phase most likely to get pulled forward, because it looks like the quick win.

11 — Open questions

Answer before design finalises

  1. Is the FSM integration bidirectional or read-only? This determines whether Create work order is a workflow or a clipboard. It gates Phase 3 and shapes the primary action.
  2. Who owns the fault-code translation library, and is it maintained per equipment family as new products launch?
  3. Does the priority model need seasonal logic in v1 — no heat in January versus July — or can that wait?
  4. Does turning notifications on by default require dealer consent under existing HVAC Partners terms?
  5. Which dismissal reasons feed alert tuning, and who reviews them?
